# TLY-103 — Identity: resource server and /v1/me

Lane: CORE · Track B (auth) · Depends: TLY-004 (merged) · Traces FR-TEN-05, NFR-SEC-02.

## Approach

1. **Resource server.** `SecurityConfig` adds a `SecurityFilterChain` matched to `/v1/**` requiring
   a valid bearer JWT (Spring Security OAuth2 resource server, Nimbus). `JwtDecoder` validates
   issuer (realm `tally-tenants`), audience (`tally.security.jwt.audience`, default `tally-api`),
   signature and expiry (Spring's default validators + a custom `AudienceValidator`). An invalid,
   expired, wrong-issuer/audience or unsigned token is rejected 401 by
   `ProblemJsonAuthenticationEntryPoint` with `code: UNAUTHENTICATED` (AC1).
2. **Identity resolution from the token, not a database.** AC2 itself says the active tenant comes
   "from the `tenant_id` claim" — so `TenantClaimAuthenticationConverter` builds the
   `AuthenticatedUser` (user id/email + active tenant + memberships) entirely from JWT claims
   (`tenant_id`, `email`, `name`, and a `memberships` claim array Keycloak populates via a protocol
   mapper: `[{tenant_id, tenant_name, role}]`). If `tenant_id` is not among the token's own
   `memberships`, the converter throws `InvalidBearerTokenException` → 401 (AC3), inside Spring
   Security's authentication pipeline so the existing entry point handles it uniformly.
3. **Permission matrix.** `Role` (`OWNER/ADMIN/DEVELOPER/FINANCE/VIEWER`, matching
   `contracts/openapi.yaml`'s `Me.active_tenant.role` enum) × `Scope` (`READ/WRITE`) in
   `PermissionMatrix`. `@RequireScope(Scope.WRITE)` on a controller method is enforced by
   `PermissionEnforcementInterceptor`, throwing `ForbiddenScopeException` → 403
   `FORBIDDEN_SCOPE` via `GlobalSecurityExceptionHandler` (AC4).
4. `GET /v1/me` (`IdentityController`) reads `AuthenticatedUserContext.current()` (a thin wrapper
   over `SecurityContextHolder`, populated by step 2) and maps it to the generated `Me` DTO.

## Ruling — membership source is the JWT, not `users`/`memberships` tables

TLY-101 (tenant provisioning) has not landed `users`/`memberships` tables yet (checked: its branch
is still at the same commit as `main`, no schema divergence). Rather than block on it or invent a
competing migration, TLY-103 takes option (b) from its brief: AC2's own wording ("from the token")
already specifies the token as the source of truth for `/v1/me`, so no DB dependency exists for this
story. `TenantContext`/RLS (TLY-102) already treats the credential as the sole source of tenant id
(ADR-002/003) — this extends the same principle to user/membership data. A later story can add a
DB-backed read model once TLY-101's tables exist (e.g. to serve richer team-management screens);
`/v1/me` itself has no such requirement. No competing migration was added; no `V1xx` number consumed
by this story.

**Follow-up (2026-09-24): re-verified against TLY-101 as actually merged, not just as planned.**
TLY-101 landed `tenancy.plan_versions`, `tenancy.tenants`, and `tenancy.invitations` (pending
invites — email/role/status, not accepted memberships); it does **not** add a `tenancy.memberships`
or `tenancy.users` table. A durable, queryable membership record is TLY-107's scope ("Team members
and invitations", Sprint 3): accepting an invitation is what creates the membership row. So this
Ruling's original premise ("TLY-101 hasn't landed yet") is now stale, but its conclusion still
holds for a stronger reason — there is no membership table for `/v1/me` to read from at all, and
AC2 names the JWT claim as the source regardless. This is not a cross-story gap needing
reconciliation; it's the correct design as written. Revisit once TLY-107 lands: at that point decide
whether `/v1/me` should read live `tenancy.memberships` rows instead of trusting the JWT's embedded
`memberships` claim, since an admin changing someone's role won't be reflected until they get a new
token under the current design.

## Ruling — matrix granularity

docs/02 §7.1 references "a `Permission` matrix" but does not publish one; docs/06 only pins down
"VIEWER is read-only, everyone else can write" (TLY-107's "Only OWNER/ADMIN can manage the team"
is a *finer* per-endpoint rule for a later story, not a contradiction). TLY-103 ships the coarse
READ/WRITE matrix AC4 actually asks for; a finer per-resource matrix is deferred to whichever story
needs it, since building one now would be speculative (YAGNI).

## Ruling — management port now 401s instead of 404ing unmapped paths

`PortsIT.should_answer_not_found_when_the_tenant_api_is_called_on_the_management_port__TLY_004_AC4`
(TLY-004) asserted 404 for `/v1/me` called on the actuator/management port. Putting Spring Security
on the classpath makes Boot auto-configure `ManagementWebSecurityAutoConfiguration` for that port's
(separate child-context) `SecurityFilterChain`, which now authenticates every request there —
including ones with no mapping — before the dispatcher can 404 them. Two ways to suppress it for
just that child context (a class exclude on `CoreApplication`'s `@SpringBootApplication`, and a
`spring.autoconfigure.exclude` property) were tried and neither reached the child context. The
AC's actual intent — the management port never serves tenant-API content — still holds under 401,
so the test's expected status was updated to 401 with a comment explaining why, rather than treated
as a story to chase further; re-open if a cleaner suppression is found later.
