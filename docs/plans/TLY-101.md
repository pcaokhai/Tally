# TLY-101 — Tenant provisioning and plan versions

Lane: CORE · Track B (full ceremony: tenant data, idempotency) · Depends: TLY-004, TLY-102 (merged
5f4b739) · Traces FR-TEN-01, FR-TEN-02, ADR-028.

## Migration number

Reserves **V100** in the V100-V199 range (docs/05 §5; TLY-102 reserved none, see its Ruling).

## Approach

1. `V100__tenancy_provisioning.sql`:
   - `tenancy.plan_versions` (platform data, no `tenant_id`, no RLS — ADR-028) seeded with
     `starter v1`, `growth v1`, `scale v1`; `limits jsonb` carries `isolation_tier` when a plan
     forces SILO.
   - `tenancy.tenants` (platform registry, no `tenant_id` column — it *is* the tenant root, no RLS)
     referencing `plan_versions`.
   - `tenancy.invitations` (tenant-scoped, RLS per TLY-102 convention) — the owner invitation AC1
     asks for.
   - `billing.invoice_number_seqs` (tenant-scoped, RLS, PK `tenant_id`, one row per tenant).
   - `ledger.accounts` (tenant-scoped, RLS) — default chart of accounts rows are inserted by the
     use case, not seeded by the migration (they depend on the tenant id).
   - `kernel.audit_log` (id, tenant_id nullable, actor, action, payload jsonb, created_at) — **not**
     RLS-scoped: operators need cross-tenant read for `/ops/v1` audit views, and the full
     ops-audit design (hash chain, append-only trigger) is a later story (docs/06 `ops.operator_audit_log`
     is the operator-side audit; `kernel.audit_log` here is the minimal domain-event audit this AC
     needs). Recorded as a Ruling below.
   - `GRANT USAGE ON SCHEMA` for tenancy/billing/ledger (kernel already granted in V001) plus
     table grants to `tally_app`, per TLY-102's convention.

2. Application code (module `tenancy`, hexagonal):
   - `domain`: `PlanVersion`, `Tenant`, `IsolationTier` records (no framework imports).
   - `application`: `CreateTenantUseCase` — looks up the plan version, decides `isolation_tier`,
     inserts tenant + invitation + invoice-number-seq row + default ledger accounts inside one
     `@Transactional` method, binding a `TenantContext` for the *new* tenant id for the duration
     (the caller is an operator with no tenant claim, but RLS `WITH CHECK` on the tenant-scoped
     rows this insert touches requires the new tenant to be current). Writes the `tenant.created`
     audit row inside the same transaction.
   - Minimal idempotency (AC1): `kernel.idempotency_keys(key text PK, response jsonb NULL, created_at)`
     — TLY-110 will generalize this into a shared filter; this story only needs "same key ⇒ same
     response" for one endpoint, so it is a small helper in `application`, not a filter. The claim
     is a row insert (`response` starts NULL) so two concurrent requests for the same key race on
     the primary key conflict instead of both reading "not found" from a plain lookup and both
     provisioning a tenant — the loser blocks on the winner's row lock (`SELECT ... FOR UPDATE`)
     and replays its committed response once available. Recorded as a Ruling below, revised after
     the independent review caught the original read-then-write version's race.
   - `adapter/out`: `JdbcTenantRepository`, `JdbcPlanVersionRepository`, `JdbcIdempotencyStore`
     using `JdbcClient`, methods `@Transactional` (ArchUnit rule from TLY-102 requires this).
   - `adapter/in/web`: `TenantProvisioningController implements OpsTenantsApi` (generated from
     `contracts/ops-openapi.yaml`).

3. Gradle: `contracts/ops-openapi.yaml` is not generated yet (only the tenant spec is wired in
   `core/build.gradle.kts`). Adds a second `openApiGenerate`-family task (`openApiGenerateOps`)
   producing `com.tally.core.opsapi(.model)`, wired into `compileJava` and the `main` source set,
   mirroring the existing task. This is a build file change inside `core/**`, not a contract change.

4. `TenantContextHolder` gets one small addition: a package-visible `runWith` used only by
   provisioning to bind the new tenant's id for the insert transaction (the existing `TENANT`
   field was package-private with only `TenantFilter` as a writer).

## Rulings

1. **Minimal idempotency store, not the full filter — and fixed to claim-then-work, not
   read-then-work, after independent review.** TLY-110 (later sprint) generalizes
   `Idempotency-Key` handling into a shared filter/interceptor for every money-moving/creating
   write. This story implements the narrow behavior AC1 needs (same key ⇒ same stored response)
   directly in the use case against `kernel.idempotency_keys`, so it isn't blocked on TLY-110. The
   first version did `findIdempotentResponse` (a plain `SELECT`) before doing the work and saved the
   response with `INSERT ... ON CONFLICT DO NOTHING` afterwards — the independent review (HIGH
   finding) correctly caught that two concurrent requests with the same key would both read a miss
   and both fully provision a tenant before either write landed, since the `ON CONFLICT` only
   dedupes which response wins, not whether the work runs twice. Fixed to claim the key with an
   INSERT first (`TenantProvisioningPort.claimIdempotencyKey`); the loser blocks on the winner's row
   lock (`awaitIdempotentResponse`, `SELECT ... FOR UPDATE`) and replays its committed result, or
   retries the claim (bounded, `MAX_CLAIM_ATTEMPTS = 3`) if the winner rolled back.
2. **Plan version `isolation_tier` is parsed as JSON, not string-matched.** The first version checked
   `limits.contains("\"isolation_tier\": \"SILO\"")` against the driver's raw jsonb-to-text
   serialization — flagged MEDIUM by the independent review as fragile against a whitespace change
   Postgres/the driver make with no test signal. Fixed to `objectMapper.readTree(...).get(...)`.
3. **`kernel.audit_log` IS RLS-scoped, revising the plan's original assumption.** `TenantRlsConventionIT`
   (TLY-102) enforces its coverage query with no carve-out for "operator-only" tables — every table
   with a `tenant_id` column gets `ENABLE`/`FORCE` RLS, no exceptions — and CLAUDE.md §9 forbids
   weakening that test to make CI pass. `kernel.audit_log.tenant_id` is nullable for pure platform
   actions, so its policy is `USING/WITH CHECK (tenant_id = kernel.current_tenant() OR tenant_id IS
   NULL)`: tenant rows still fail closed under RLS for any other tenant's context, while
   platform-level (NULL-tenant) rows stay visible/insertable regardless of context. Discovered
   mid-implementation when the integration suite caught it — recorded here rather than silently
   narrowing the coverage test.
4. **Unit `test` task keeps `DataSourceAutoConfiguration` enabled, only Hikari's fail-fast
   disabled.** TLY-101 is the first component needing a `JdbcClient` bean, and this is the first
   story to hit the "unit test task stays Docker-free" constraint from a real DB-backed adapter.
   `@ConditionalOnBean(DataSource.class)` on the new `@Repository`/`@Service`/`@RestController`
   classes looked like the fix but is unreliable for regular component-scanned beans (confirmed by
   running the built app: the controller silently failed to register even with a real Postgres
   present — a known Spring Boot ordering gotcha for `@ConditionalOnBean` outside a dedicated
   `@Configuration`/autoconfiguration class). The actual fix: keep `FlywayAutoConfiguration`
   excluded (no real migration attempt) and set
   `spring.datasource.hikari.initialization-fail-timeout=-1` so Hikari never validates connectivity
   at startup — the full-context unit tests that exercise this path never issue a query, so nothing
   needs a real database. `PostgresKafkaIT` still overrides both properties for real integration
   tests.
5. **`openApiGenerateOps` gradle task added.** `contracts/ops-openapi.yaml` already exists and is
   referenced by this story's contract, but no Gradle wiring generated stubs from it yet — this is
   additive build config in `core/build.gradle.kts`, not a contract edit.
