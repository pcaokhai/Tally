# TLY-102 — Tenant context and row-level security

Lane: CORE · Track B (full ceremony) · Depends: TLY-004 (merged) · Traces NFR-SEC-01, NFR-SEC-02,
ADR-002, ADR-003, ADR-027.

## Approach

1. `TenantFilter` (servlet filter) resolves the tenant id from the credential only — a bearer JWT's
   `tenant_id` claim (signature verification deferred to TLY-103's real Keycloak validation; this
   story only wires the propagation mechanism), or a placeholder test API key
   `tly_test_<tenantId>` (TLY-101 replaces this with a hashed `api_keys` lookup). Anything the
   caller puts in a header/query/body is never read for this purpose.
2. The resolved id is bound into a `ScopedValue<TenantContext>` (`TenantContextHolder`) for the
   dynamic extent of the request — no `ThreadLocal`, so nothing can leak onto a reused virtual
   thread.
3. `TenantAwareDataSource` wraps the Boot-managed `DataSource` bean (via a static
   `BeanPostProcessor` in `TenantConfig`, so it also wraps whatever Flyway uses — see the
   migration-number ruling below). On `getConnection()`:
   - context bound → `SET LOCAL app.tenant_id = '<uuid>'` on that connection.
   - context unbound → nothing is set, and a WARN `tenant_context_missing` is logged.
   Because Spring's transaction manager obtains exactly one connection per transaction and holds it
   for the transaction's lifetime, this runs before the first statement of every transaction, and
   `SET LOCAL` auto-reverts at commit/rollback so pooled connections never leak state.
4. RLS itself does the fail-closed work: `kernel.current_tenant()` (already shipped in V001) reads
   `app.tenant_id` and returns NULL when unset; every policy compares `tenant_id = kernel.current_tenant()`,
   which is never true for NULL.
5. An ArchUnit rule (`sqlInAdapterOutRunsInATransaction`) fails the build if a class under
   `..adapter.out..` calls JdbcClient/JdbcTemplate/EntityManager/Statement/Connection from a method
   that isn't `@Transactional` (method or class level) — the guarantee AC2 needs (SET LOCAL only
   works inside a transaction) has to hold for every adapter, not just the ones this story wrote.

## Ruling — no migration reserved in V100-V199 by this story

TLY-102 has no real tenant table to migrate yet (TLY-101 owns `tenancy.tenants` etc.). The
RLS/composite-FK convention below is proven against two throwaway tables
(`kernel.rls_probe_parent`/`_child`) created and dropped inside `TenantRlsConventionIT` itself, not
via a Flyway migration — so no `V1xx` number is consumed here. **TLY-101 reserves the first real
number in the V100-V199 range for its own tables.**

## Ruling — role separation deferred

Making the app connect as `tally_app` (LOGIN + password) instead of the default superuser
(`${TALLY_DB_USER:postgres}`) is real production hardening implied by ADR-002 ("the app role has no
BYPASSRLS") but touches `spring.datasource.*`/secret wiring beyond a mechanism story. TLY-102 proves
the mechanism (SET LOCAL app.tenant_id; RLS fails closed) using `SET ROLE tally_app` inside the test
itself. **TLY-101 or a dedicated ops story should wire the real runtime credential** before any
tenant data is live.

## The convention TLY-101/TLY-103 must follow for every new tenant table

```sql
CREATE TABLE <schema>.<table> (
  tenant_id uuid NOT NULL,                 -- always first column, always NOT NULL
  id uuid NOT NULL,
  ... ,
  PRIMARY KEY (tenant_id, id));            -- or UNIQUE (tenant_id, id) if PK is just (id)

-- Composite FK to any intra-tenant parent (ADR-027):
ALTER TABLE <schema>.<table>
  ADD FOREIGN KEY (tenant_id, parent_id) REFERENCES <parent_schema>.<parent>(tenant_id, id);

ALTER TABLE <schema>.<table> ENABLE ROW LEVEL SECURITY;
ALTER TABLE <schema>.<table> FORCE ROW LEVEL SECURITY;     -- ADR-002: applies even to the owner
CREATE POLICY tenant_isolation ON <schema>.<table>
  USING (tenant_id = kernel.current_tenant())
  WITH CHECK (tenant_id = kernel.current_tenant());
GRANT SELECT, INSERT, UPDATE, DELETE ON <schema>.<table> TO tally_app;
GRANT USAGE ON SCHEMA <schema> TO tally_app;               -- once per schema
```

`RlsCoverageIT`-equivalent discovery query (used by `TenantRlsConventionIT`, generalize it for real
tables once TLY-101 lands):

```sql
SELECT c.relnamespace::regnamespace || '.' || c.relname
FROM pg_class c
JOIN information_schema.columns col
  ON col.table_schema = c.relnamespace::regnamespace::text
 AND col.table_name = c.relname AND col.column_name = 'tenant_id'
WHERE c.relkind = 'r' AND (NOT c.relrowsecurity OR NOT c.relforcerowsecurity);
```
Any row returned is a table that forgot RLS/FORCE — the coverage test asserts this is empty.

## Review log

Independent review (general-purpose agent, Track B second pass): no CRITICAL/HIGH blockers.
Findings: (1) `UUID#toString()` embedded in `SET LOCAL` is genuinely injection-safe (JDK format is
fixed hex+dashes) — no issue. (2) unverified JWT decode is clearly scoped/commented as a TLY-103
stopgap — acceptable. (3) `ScopedValue` lifetime is correctly bounded to the request — no leak.
(4) fail-closed behavior holds as long as AC5's ArchUnit rule is airtight. (5) **MEDIUM-HIGH**:
`sqlInAdapterOutRunsInATransaction`'s `isSqlApi` didn't recognize jOOQ (`org.jooq.DSLContext` etc.),
which the `ledger` module uses per core/CLAUDE.md instead of JPA — fixed by adding jOOQ's
`DSLContext`/`Query`/`ResultQuery` to the recognized SQL API list, and documented the rule's
non-transitive (direct-calls-only) limitation in its javadoc so it isn't assumed to catch delegated
calls. (6) the two Rulings above (no migration reserved yet; role separation deferred) were judged
reasonable scope cuts, not hidden gaps. Merge recommendation: **approve with follow-ups** — the jOOQ
fix was applied inline before merge; no further follow-up required for this story.
